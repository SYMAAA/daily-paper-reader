# DCKV: Learned Transform Coding of the Prompt KV Cache in Hybrid Language Models 

Egor Maximov 1 Aleksei Merkelov 1 Vasiliy Alekseev 1 Ivan Krivorotov 1

Valentin Beliaev 1 Nikita Arsenin 2 Dmitry Bocharov 2 Aleksei Goncharov 11MIL Team 2DAIMLD 

Abstract 

Hybrid language models keep a key–value (KV) cache only in their few full-attention lay-ers, but this cache is still the part of a prompt’s state that grows with the prompt and that must be stored or moved to reuse it. We present DCKV, a differentiable codec for the KV cache and the first KV-cache codec that is trained end to end. Its transform, its quantizer and its entropy models, which are conditioned on the prompt tokens and on already decoded neighbouring positions, are optimized together against the frozen language model, both for the code length that the entropy models assign and for the change of the model’s output. On Qwen3.5-2B, DCKV stores a compressed to-ken in more than 55 times fewer bytes than bf16 at a loss of at most 1.8 points on three long-context benchmarks, and in more than 100 times fewer bytes at a loss of at most 3.6 points. 

1 Introduction 

Reusing the key–value (KV) cache of a long prompt saves its prefill, which dominates the time to the first token on long inputs. To reuse prompt caches, serving systems keep them outside GPU memory and move them between devices and ma-chines [30, 31]. Because such a cache is written once and read one or more times, a codec for it can afford entropy coding. What matters is the number of stored bytes at a given answer quality [43]. Recent hybrid models interleave a few full-attention layers with linear-attention or state-space layers [28, 39]. In Qwen3.5-2B, 6 of the 24 lay-ers use full attention, and the other 18 are Gated DeltaNet layers [46] with a recurrent state of fixed size, 9.84 MiB per request. Although the KV cache is small, 12,288 bytes per token in bf16, it is still the only part of the state that grows with the prompt, to 48 MiB at 4K tokens and 1.5 GiB at 128K. We judge a codec by the memory of a stored request, recurrent state included. KV cache transform coding (KVTC) [43] decor-relates keys and values with PCA, allocates bits by dynamic programming and applies a general-purpose lossless coder. Its transform and its bit allocation minimize the reconstruction error of the cache and do not see the output of the model. Learned image and video codecs train the transform and the quantizer on a rate–distortion objective [4] and condition the entropy model on what the de-coder already has [5, 18]. For a language model, the natural distortion is the change of its output distribution, which some methods that compress the cache for decoding already use to learn cache projections [29]. We present DCKV, a Differentiable Codec for the KV cache. It is a learned codec for the stored prompt cache of a hybrid model and the first KV-cache codec whose transform, quantizer and en-tropy models are trained end to end. Our contribu-tions are: • A codec with one joint transform for the keys and values of all attention layers, linear with a small nonlinear correction, with a learned quantization step for each component and GPU rANS coding, trained against the frozen model on the code length plus the KL diver-gence of the output (§3). • Conditional entropy models that predict each code from the embedding of its token and from already decoded neighbouring tokens, trained together with the transform. With the correction they remove 12–16% of the bytes at the same quality; fitted in closed form to a codec that is already trained, they give a simi-lar saving on RULER 4K without retraining (§3.4, §5.2). • An evaluation on Qwen3.5-2B with paired per-task comparisons and a memory account-ing that separates the state of a request from 1arXiv:2610.36950v1 [cs.LG] 27 Oct 2026 the codec weights (§4, §5). Over three rates, DCKV needs 72% fewer bytes than KVTC at equal score on RULER 4K and 62% fewer on LongBench. At prompts of 4K to 11K tokens the recurrent state takes about three quarters of the memory of a stored request. A smaller payload then reduces the request memory by a much smaller fraction than the stored cache. At 32K tokens, where the payload of DCKV is more than a third of the request mem-ory, DCKV scores 6.5 points higher than KVTC at about the same request memory (§5.3). 

2 Related Work 

Hybrid models. Hybrid models replace most at-tention layers with layers whose state does not grow with the context, such as Mamba layers in Jamba [28] or Gated DeltaNet layers [46] in Qwen3.5 [39]. Reusing a prompt in such a model needs both the attention cache and a snapshot of the recurrent state [37]. The recurrent state has a fixed size and can be compressed by its own means, for example by quantization to a few bits [12], while the attention cache grows with the prompt and holds what the model must retrieve exactly [1]. DCKV compresses the attention cache and keeps the recurrent state exact, so methods for the recur-rent state can be used together with it. 

KV cache compression for decoding. Most methods shrink the cache while the model de-codes, by evicting tokens [27, 48], by quantizing keys and values [20, 32], by projecting them to a lower rank [10, 29], or by sharing them across layers [9, 11]. Some of them learn their projec-tion or their selection through the output of the model [29, 41]. All of them keep a cache of fixed width that attention can read directly, and this re-quirement rules out codes of variable length [15]. Their cache size is set by a design choice, such as a rank, a bit width or a number of tokens, and the statistical redundancy inside that width stays in the cache. Because a stored cache is read only when its prompt is reused, an entropy coder can remove this redundancy, also after eviction or rank reduction. 

Learned compression. Learned image codecs train a transform, a quantizer and an entropy model together on the rate plus λ times the dis-tortion [3, 4]. Their entropy model is conditioned on information that the decoder already has, a side latent [5] or already decoded latents, which the checkerboard order decodes in parallel [18]. Video codecs add conditioning on the previous frame and serve several rates with one model [25, 26]. The same recipe has been used for intermediate features in split inference, where a bottleneck with a learned prior is trained into a vision model [34]. For lan-guage models, an analysis of split transformer in-ference trains small models such as GPT-2 Small together with a codec for one hidden state [13]. In these works the network is trained together with its codec. A codec for the KV cache of a deployed model must work with a model that is already trained, on an input that grows with the prompt. DCKV is trained against the frozen model and works with a released model as it is. The same objective could also be added to pre-training. 

Entropy-coded storage of KV caches. Codecs for a stored or transferred cache do use an entropy coder, and they differ in what comes before it. Some quantize the cache directly or after a fixed rotation and code it with arithmetic, Huffman or rANS codes, under distributions that are profiled offline or fixed [23, 31, 44]; KVCodec uses a hard-ware video codec [35]. Others first remove the correlation in the cache, by PCA with bit alloca-tion in KVTC [43], by prediction from other layers or heads [42, 47], or by bit allocation from rate– distortion theory [50]. Codec-Gauge comes closest to a learned codec, as it trains channel transforms around an existing codec with a smooth proxy of the rate [24]. In all of them the probability model is fixed or profiled, and none trains its transform, quantizer and entropy model through the length of the code and the output of the model. To our knowl-edge, DCKV is the first KV-cache codec that does, and its entropy models also use what the decoder of a stored prompt has, the prompt tokens and the already decoded neighbours.

3.4 Conditional entropy models 

The static model ignores what the decoder already knows. DCKV replaces it with two conditional models, which shift the Laplace distribution of each code by a predicted mean. 

Token-conditioned model. The decoder knows the prompt tokens, because a request that reuses a stored prompt cache contains the prompt text. We do not count the token ids in the payload (as 4-byte integers they would add 1–5% at our rates). The model predicts the coefficients of to-ken t from the input embedding e(wt) of its to-ken, μt = e(wt) AB + c, with A ∈ R2048 ×r and

Encoder and de-coder select the same table as long as they compute the same predictions; all our evaluations encode and decode in the same process (see Limitations). 

Checkerboard context model. The codes of neighbouring tokens are correlated, but a model that predicts every token from the one before it has to decode the tokens one by one. We instead split the positions of the compressed region into even and odd ones, the one-dimensional form of the checkerboard order of image codecs [18]. Even po-sitions are coded first, with the token-conditioned model alone. Odd positions are coded second, when both of their neighbours are already decoded. A linear map of rank 1024 predicts the mean of the codes of an odd position from the dequantized coefficients of its two neighbours and from the em-bedding of its own token. Each pass is parallel over tokens, so a cache is decoded in two parallel steps for any length.

Because the rate is measured under the conditional models, the transform learns to leave to the codes what these models cannot predict. The conditional models start from a closed-form fit to the untrained codec, and several codecs train in one loop on shared pre-fills. Rounding has a zero gradient almost everywhere. The usual proxy adds uniform noise u ∼ U (− 12 , 12 )

to yt,k /∆k in both terms of the loss [4]. For a component with βk ≤ 0.2, rounding sets more than 90% of the coefficients to zero. Because the noisy coefficients still carry their signal to the de-coder during training, we expect the KL term to underestimate the distortion of the real codec. The noise-based rate, in turn, overestimates the entropy of the rounded code by a factor of 1.47 at βk = 0 .2

and 5.66 at βk = 0 .1 (Appendix A). We therefore use mixed quantization [36], which computes the rate on the noisy coefficient and reconstructs from the rounded coefficient with a straight-through gra-dient [7, 45]. This estimator can degrade nonlinear transforms at low rates [3]; our correction is trained with it and gains most at low rates (Appendix B). A codec trained with one λ serves one rate. Two cheaper ways to change the rate, a factor on all steps of a trained codec and one codec trained for a range of λ, cost bytes or quality (Appendix B). 

3.6 Memory accounting 

The request memory is what a stored request needs besides the model: the payload, the 132 uncom-pressed positions (1.55 MiB) and the recurrent state (9.84 MiB); for the uncompressed model, the full attention cache and the same recurrent state. Since codec weights are loaded once with the model and shared by all requests, we count them as model weights for all codecs. We report them separately: 176 MiB of fp32 parameters for DCKV, about 5% of the weights of the 2B model, 96 MiB for the linear codec and 10–20 MiB for KVTC. Peak GPU memory grows by 182 MiB with DCKV and by 102 MiB with the linear codec (Appendix F). 

4 Experimental Setup 

Model and benchmarks. We use Qwen3.5-2B [39] in bf16 with greedy decoding, one request at a time, with Hugging Face Transformers on one A100 40GB GPU; generative benchmarks use the chat template in non-thinking mode. RULER [21] at 4K tokens has 13 tasks, 1,287 samples and a mean prompt of 3,742 tokens, and we score it by to-ken recall, the fraction of the words of the reference answer found in the generated answer. RULER at 32K tokens has the same 13 tasks, 1,297 samples and its own uncompressed reference. From Long-Bench [2] we use 18 of the 21 tasks, with a mean prompt of 10.8K tokens and a re-implementation 4of the official metrics. We leave out LCC and RepoBench-P, on which no run of our codecs, of KVTC or of the uncompressed model scores more than 4.4 points, and SAMSum, on which, as on RepoBench-P, every run of our codecs and of KVTC scores above the uncompressed reference (31 and 30 runs; Appendix H). If we include all 21 tasks (20 for DCKV at λ = 5 ·10 4), every loss is 0.3–1.0 points smaller and the order of the methods does not change. MMLU [19] has 57 subjects, 5-shot, scored by the likelihood of the answer options, with a mean prompt of 620 tokens. Appendix E gives two benchmarks with shorter prompts, GPQA Diamond and IFEval. 

Baselines. We found no official implementation of KVTC [43]. We start from a public proof of concept 2, which allocates bits greedily, and replace this allocation with the dynamic programming of the paper. At 16 × the greedy allocation loses 13.0 points on RULER 4K, and the dynamic program-ming loses 0.53. Our KVTC uses two PCA bases of rank 1024, for the keys before RoPE and for the values of all attention layers, bit allocation for a nominal compression ratio, and DEFLATE. Its ratios of 16 ×, 24 × and 32 × give 627, 410 and 304 bytes per token on RULER 4K. We allow all widths from 0 to 8 bits. Restricting the code widths to 0, 2, 4 and 8 bits, the widths closest to the data types of the KVTC paper, saves 6–10% of the bytes at 8× and 16 × with a slightly smaller loss, but at 

32 × it loses 7.2 points on RULER 4K instead of 3.9. xKV [11], a cache compression method for decoding, projects the keys and values of each pair of adjacent attention layers onto a shared low-rank basis from a singular value decomposition; we use rank 192 for keys and 288 for values. xKV com-putes the basis for each prompt, so we count the basis (2.8 MiB) in the request memory and in the payload, together with the 16-bit coefficients of all prompt tokens. The ablations use the trained linear codec (§3.2) and two untrained codecs with the quantizer and coder of DCKV. One keeps KVTC’s separate key and value bases with one uniform step (separate bases ), and the other is the untrained joint basis .

Comparisons. A score change is the paired dif-ference of benchmark means over the tasks that both runs share, reported with the number of tasks 

n. For two codecs we also count the tasks on which the first is better, equal and worse (W/T/L) and ap-ply a two-sided sign test over the tasks that differ; Table 8 in Appendix D lists these statistics. The evaluation is deterministic, and repeated launches of a configuration, also on two versions of the eval-uation code and on two GPUs in parallel, give iden-tical scores on every task. The only uncertainty in a difference between two runs comes from the finite numbers of samples and tasks; two uncom-pressed runs with about 50 and 100 samples per task differ by 0.09 points on the RULER 4K mean and by up to 4 points on single tasks. For two rate– quality curves we also give the Bjøntegaard delta rate (BD-rate) [8], the mean difference of the log payload at equal score over the range of scores that both curves cover, in percent. With three to five points per curve, we interpolate linearly and read the value as an estimate [6]. Bytes per token count the compressed region only.

5.3 Similar request memory 

The recurrent state takes 81% of the request mem-ory of DCKV on RULER 4K, 73% on LongBench and 54% on RULER 32K (Figure 3; Tables 11 and 12 in Appendix F). On RULER 4K, KVTC needs at most 12% more request memory than DCKV, and no difference between them is signif-icant. On LongBench and RULER 32K, DCKV scores 2.4 and 6.5 points higher than KVTC at 732 ×, which needs 8% and 7% more request mem-ory. Only KVTC at 16 × is not significantly worse than DCKV there (on LongBench it is 1.44 points better), and it needs 32% and 55% more request memory. At λ = 10 5, DCKV needs 5–22% less request memory than KVTC at 32 × and still scores higher on all three benchmarks. 

5.4 Behaviour by task 

Figure 7 in Appendix H shows the change of ev-ery task. On RULER 4K one question-answering task loses 3.3 points with DCKV and no other task more than 1.3. On RULER 32K, variable tracking loses 4.2 points and the same question-answering task 3.7. On LongBench, passage retrieval loses most, 10.0 points in English and 6.0 in Chinese, against 4.0 and 1.0 with KVTC at 16 × and 11.5 and 12.5 at 32 ×. At λ = 10 5, variable tracking loses most on RULER, 5.8 points at 4K and 11.0 at 32K. Common-word extraction loses 3.4 points at 4K, and a needle with a UUID value loses 3.0 at 4K and 6.0 at 32K. On LongBench, passage retrieval loses 27.0 points in English and 12.5 in Chinese. 

6 Conclusion 

DCKV trains the transform, the quantizer and the conditional entropy models of a codec for the stored prompt cache of a hybrid language model end to end, against the frozen model. On Qwen3.5-2B it stores the cache in about 210 bytes per token, 2.9 times fewer than KVTC at the same loss on RULER 4K, and its advantage grows at stronger compression. Over three rates it needs about a third of the bytes of KVTC at equal score on RULER 4K and LongBench (§5.1). The ablations show that each part adds to this gain, from entropy coding and the joint basis to the training against the output of the model and the conditional entropy models (§5.2). A smaller payload matters most for long prompts, because at moderate lengths the recurrent state takes most of the memory of a stored request; at 32K tokens DCKV scores higher than KVTC at about the same request memory (§5.3). Since the codec is trained against a frozen model, it can serve a released model without changes to its weights. Open questions are whether the results carry over to other hybrid models, how to train one codec for a range of rates without a loss at the upper end, and how to make decoding give identical results on different devices. A model that is pre-trained together with the codec, with the code length of its cache in the loss, may give a cache that compresses even better. 

Limitations 

One model, few tasks. We developed the codec on Qwen3.5-0.8B, but all results are for Qwen3.5-2B, and we did not test other hybrid families. The evaluation is deterministic, but with 13 and 18 tasks many differences between strong codecs are not sig-nificant under the sign test, and we did not compute intervals over samples or correct the p-values for multiple comparisons. We cannot yet say why a few tasks, such as variable tracking and passage re-trieval, lose much more than the others, because we have not analysed the answers sample by sample. 

Rate control. Each rate needs its own codec and its own training run. We also implemented and tested one codec for a range of λ with the mech-anism of variable-rate video codecs [26]. It falls behind the codecs for one λ at the upper end of the range, and we did not find the cause (Appendix B). A factor on the steps of a trained codec changes the rate without training but costs bytes. 

Frozen model. We train the codec for a frozen language model, which lets it work with a released model as it is. Continued pre-training can make a KV cache easier to compress for post-hoc meth-ods [16]. A model that is pre-trained together with the codec, with the code length of its cache in the loss, may also give a cache that compresses better, but we did not have the compute to test it. 

Context length. The codecs were trained on 4K-token prompts and evaluated on prompts of up to 32K tokens. Beyond 32K tokens the curves of Figure 3 are computed, not measured. At 32K tokens the measured payload per token is 3% above that on RULER 4K for DCKV and 12–14% below it for KVTC, so the computed curves overstate the advantage of DCKV. 

Codec weights and peak memory. Because DCKV restores the full bf16 cache before decod-ing, it does not reduce peak GPU memory or the time per output token. Its weights add about 5% to the size of the 2B model, and peak GPU memory grows by about the size of these weights (§3.6). 

Latency. We timed the uncompressed model, KVTC at 16 × and DCKV once, one after an-other on one A100 of a shared node (Table 10, 8Appendix F). With a stored cache, the time to the first token, which includes decompression, is 115 ms for DCKV at 4K tokens and 287 ms at 32K, against 862 and 4,601 ms with the prefill of the uncompressed model. We did not time the com-pression alone, and the time per output token does not change. The time of KVTC on our shared node is not stable, with 6.8 s at 32K in this run and 0.6 s in an earlier one. 

Baselines and evaluation. Our KVTC has one quantization range per component for the whole prompt and no block sizes or data types; the paper chooses them per block of components, and we did not evaluate that variant or compare with the num-bers of the paper. On MMLU every run of DCKV, the linear codec and KVTC loses 0.5–1.5 points whatever its payload. This loss may come from the part of our evaluation harness that runs a com-pressed cache rather than from the compression. On IFEval and on two LongBench tasks that we leave out of the means, every run of our codecs and of KVTC scores above the uncompressed reference (Appendices E and H). We did not find the cause of these offsets. 

Decoding on another device. All our evaluations encode and decode in the same process. Since the conditional models compute their predictions in floating point, decoding on another device needs predictions that are identical bit for bit, for example from integer inference as in DCVC-RT [22]; we have not verified this.

B Additional Ablations 

Step multiplier instead of retraining. Scaling all steps of a trained codec by one factor moves it along the rate axis without training. For the linear codec at λ = 3 ·10 5, halving the steps adds 0.51 points on RULER 4K (9/3/1; p=0 .02 ) at 521 against 282 bytes per token, and quartering them scores 0.40 points lower on RULER 4K than halving them (0/9/4) at 762 bytes. The linear codec trained at λ = 10 5 with halved steps scores like the one trained at 3·10 5 (+0 .13 points; 8/1/4) but needs 24% more bytes (350 against 282). Fitted to the linear codec of Table 1 (second block), the token model saves 4.3–4.6%, the token and neighbour models 6.8–11.7%, and long streams bring the saving to 15.6%, again with identical scores.

Other variants. Several variants gave little or nothing, and DCKV does not use them. A nonlinear correction or corrections for 16 groups of tokens, added to a trained linear codec for 0.3B more tokens, saved 1.3–2.7% of the bits at about the same training loss. Separate bases of rank 3072 instead of 1024 added 22% to the payload for +0 .21 points on RULER 4K. The following measurements were made offline, on caches of Qwen3.5-2B with the KL divergence of next-token distributions as the quality measure. Coding each attention layer with its own basis, conditioned on the reconstructed previous layers, cost 13–27% more bits than the joint basis at equal KL divergence, because the conditioning layers are themselves reconstructed with error. A mixture of 16 PCA bases, one per group of tokens, used 18–25% fewer bits than one basis but needs about 1.2 GB of weights. On Qwen3.5-0.8B, a learned hyperprior [5] saved at most 1.2% of the payload on top of the token-conditioned model. 15 KVTC closer to the original. In an offline measurement, a KVTC built as in the original paper, with exact dynamic programming, blocks of 1 to 1024 consecutive components, a data type and a 16-bit offset and scale per block, and DEFLATE, needed 30–53% fewer bits at equal KL divergence than KVTC with greedy bit allocation. It was not compared with the KVTC with dynamic-programming allocation that the benchmarks use.

Payload and expected code length. The code length that a trained entropy model expects, the entropy of the rounded Laplace distribution with the trained steps and scales, is 1,944 bits per token for the linear codec at λ = 3 ·10 5 and 1,262 bits for DCKV. The stored payload on the held-out FineWeb-Edu documents is 2,048 and 1,475 bits, 5% and 17% more, and on RULER 4K it is 16% and 35% more (282 and 214 bytes per token). The difference combines two effects that we did not measure separately. The codes of a given text differ from what the model expects, more so on RULER than on the training domain, and the coder adds its own cost (the grid of 576 tables for the mean and the scale, escaped codes at 64 bits each, and the end of every rANS stream).
