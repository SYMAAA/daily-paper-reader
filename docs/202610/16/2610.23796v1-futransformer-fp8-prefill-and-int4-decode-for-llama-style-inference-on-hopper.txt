FUTRANSFORMER: FP8 PREFILL AND INT4 DECODE FOR LLAMA-STYLE
INFERENCE ON HOPPER
Wei Wang
wei.wang217@gmail.com
ABSTRACT
Transformer inference has different bottlenecks during prefill and decode. Prefill reuses weights across many
tokens and is dominated by matrix multiplication and activation data movement. Single-token decode has
limited data reuse and is dominated by weight and KV-cache reads. We present FUTRANSFORMER, a CUDA
implementation of a Llama-style Transformer block for NVIDIA Hopper GPUs. CODA showed how to express
Transformer training operators as GEMM-plus-epilogue programs. FUTRANSFORMER applies this principle to
inference. It adds direct KV-cache placement, folds the fixed RMSNorm gain into weights, writes FP8 values
directly from the producing epilogue using delayed scaling, and supports prefill without padding. For decode,
FUTRANSFORMER uses INT4 projection weights and an INT4 copy of the KV cache. Keys and weights follow
the Tensor Core fragment layout, so the kernels can dequantize them directly into MMA operands without creating
full intermediate tiles. A block-diagonal Hadamard transform makes INT4 cache quantization less sensitive to
outlier channels. On one H100, prefill is up to 1.48× faster than compiled PyTorch FP8 and reaches 1.29 PFLOP/s.
For the closest shared operation, gate/up projection followed by SwiGLU, the BF16 path is 1.13× faster than the
released CODA kernel at the 8B shape. Our FP8 inference path is 2.02–2.18× faster than the evaluated BF16
CODA path. Across the 8B and 70B shapes at batch 1 to 32, INT4 decode is 1.3–2.4× faster than whichever
PyTorch decode block is faster at each point: 2.1–3.3× faster than the compiled, CUDA-graphed BF16 block, and
1.3–6.3× faster than the same block using PyTorch’s INT4 projection kernel, which is built for a single query row
and loses to its own BF16 block at batch 32. INT4 decode is also 31–51% faster than our FP8 decode path. For
the complete Llama-3.1-8B model, one INT4 decode step takes 2.8 ms at batch one, compared with 8.1 ms for the
compiled transformers implementation. On Llama-3.1-8B, decoding every WikiText-2 token through the INT4
weight path increases perplexity from 6.24 to 7.23 with round-to-nearest weights, or to 6.99 with GPTQ weights
stored in the same format. The rotated INT4 cache adds another 0.20. The kernel path matches the quantized
reference computation to within 0.001 perplexity.

INTRODUCTION
Matrix multiplication dominates Transformer FLOPs, but
data movement and other operations also contribute to exe-
cution time. A decoder block also performs normalization,
residual updates, position encoding, activation functions,
precision conversion, and KV-cache updates. These opera-
tions perform little arithmetic but often read and write large
intermediate tensors. As Tensor Cores become faster, this
data movement takes a larger share of the total execution
time.
CODA (Guo et al., 2026) addresses this problem for train-
ing by expressing many Transformer operators as GEMM-
plus-epilogue programs. An optimized GEMM mainloop
produces an output tile. A programmable epilogue then pro-
cesses the tile while it is still on chip. This allows pairwise

operations such as RoPE and SwiGLU, as well as resid-
ual updates, scaling, and partial reductions, to run without
separate reads and writes to global memory.
FUTRANSFORMER uses the same GEMM-plus-epilogue
principle for autoregressive inference. Inference adds two
requirements. First, prefill must manage persistent state.
It must write K and V directly to the KV cache, produce
low-precision activations for later projections, and support
requests of different lengths. Second, decode has too few
rows to behave like a large GEMM. At small batch sizes,
each layer reads its weights for only a few rows, and at-
tention reads cached K and V values for every query. The
decode path must therefore reduce the bytes read and pre-
vent dequantization from delaying the main computation.
For prefill, FUTRANSFORMER uses persistent FP8 GEMMs
with epilogue policies selected at compile time. These poli-
cies apply RoPE or SwiGLU, write K and V to the cache,

collect RMSNorm statistics, restore scales, and optionally
write FP8 output directly. Inference weights are fixed, so
the learned RMSNorm gain can be folded into the next pro-
jection before quantization. The row-wise normalization
factor is then applied in that projection’s epilogue. This re-
moves the normalized activation tensor while preserving the
quantized computation. Packed inputs also remove padded
projection rows from batches with different request lengths.
For decode, FUTRANSFORMER uses INT4 weights and an
INT4 copy of the KV cache. Hopper has no INT4 Tensor
Core MMA, and its FP8 MMA requires large warpgroup
shapes that the few query rows in decode cannot fill. The
kernel must therefore expand INT4 values before a 16-bit
MMA. The main design choice is where to perform this
expansion. FUTRANSFORMER stores keys and weights in
the order required by the MMA fragments. A byte-indexed
lookup converts packed cache values into FP16 pairs. A
short sequence of logic and packed BF16 operations con-
verts weight nibbles directly in registers. Group scales are
applied after accumulation. Before cache quantization, a
block-diagonal Hadamard transform spreads large channel
values. Matching transforms on the query and attention out-
put preserve the attention computation before quantization.
The main contributions are:
• Inference-specific GEMM epilogues.
Starting
from CODA’s GEMM-plus-epilogue formulation, FU-
TRANSFORMER adds direct KV-cache placement,
folds the fixed RMSNorm gain into weights, writes
FP8 producer output with delayed scaling, and sup-
ports packed prefill.
• Fragment-aligned INT4 decode. INT4 weights and
cache entries are packed in the layout required by the
MMA fragments that consume them. Values are de-
quantized in registers or through a small lookup table.
Scales are applied outside the per-element inner loop.
• Outlier-aware cache quantization. A block-diagonal
Hadamard transform reduces INT4 cache error when
keys contain large channel outliers. Before quantiza-
tion, the transform preserves the exact attention dot
product.
• A final-result evaluation. We compare full prefill and
decode layers with PyTorch. We also compare the
complete Llama-3.1-8B model with PyTorch and the
closest shared gate/up–SwiGLU stage with CODA. We
report performance and numerical error, and label com-
parisons that use different precisions. Using a trained
Llama-3.1-8B checkpoint, we decode every WikiText-
2 token through the INT4 path and measure perplexity,
per-layer error, and error accumulated across layers.

2.2
GEMM-plus-epilogue programs and CODA
A high-performance GEMM has two parts. The mainloop
loads input tiles and performs matrix multiply-accumulate
operations. The epilogue processes and stores each com-
pleted output tile. At that point, the output is already in
registers or shared memory. The epilogue can therefore per-
form local operations without first writing an intermediate
tensor to HBM.
CODA (Guo et al., 2026) provides a structured way to use
this idea in Transformer training. It keeps the GEMM main-
loop fixed and offers five groups of epilogue operations that
can be combined: elementwise and pairwise maps; vec-
tor loads and stores; tile loads and stores; tile reductions,
with partial results combined by a small auxiliary kernel;
and stateful transforms. CODA also shows that the row-
wise RMSNorm factor can be moved through the following
GEMM and applied in its epilogue. Together, these opera-
tions cover nearly all non-attention work in the forward and
backward passes of a Transformer block.


FlashAttention introduced tiled attention designed to reduce
data movement, together with online softmax. Later work

and low precision (Dao et al., 2022; Dao, 2024; Shah et al.,

approach. Its decode design focuses on how low-bit K and

3
FUTRANSFORMER DESIGN
3.1
Overview
FUTRANSFORMER uses separate prefill and decode paths
because they have different bottlenecks. Prefill keeps large
GEMMs efficient and reduces data movement between them.
Decode reduces the bytes read for weights and the cache,
then dequantizes values in the layout required by the MMA
operands.
The prefill projection kernel uses 128×256×128 CTA tiles,
a four-stage TMA pipeline, one producer warpgroup, and
two consumer warpgroups. Its mainloop uses Hopper FP8
WGMMA and the Tensor Memory Accelerator (NVIDIA,
2026a). An epilogue policy selected at compile time con-
trols how each completed fragment is processed and stored.
The QKV, output, gate/up, and down projections can there-
fore perform different inference operations while sharing
one optimized GEMM mainloop.
The decode path has two kernel families.
A register-
streaming kernel handles M = 1, and a skinny matrix
kernel handles 2 ≤M ≤32. Both read packed INT4
weights and expand them directly into MMA fragments for
accumulation with BF16 activations. Decode attention reads
the INT4 cache copy. For long contexts, it uses split-KV
reduction.
3.2
Inference-aware FP8 prefill
3.2.1
Direct KV-cache placement
In training, K and V are activations used later in the same
pass. In inference, they must be written to persistent cache
addresses. A conventional implementation first writes dense
K and V tensors, then launches another kernel to scatter
them into the cache. FUTRANSFORMER writes them to the
cache directly from the QKV epilogue.
For each output row m, metadata gives the request and token
position pm. The epilogue maps each output column to a
head and channel in Q, K, or V. It restores the projection
scales, applies RoPE to Q and K, writes Q in the layout used
by attention, and stores K and V at
offset(request(m), head, pm, channel).

FUTRANSFORMER uses delayed per-tensor scaling. Invo-

must have a valid initial scale. A scale must also be de-
fined for all-zero tensors. Concurrent request groups must
keep separate scale states unless they are intentionally run
together. Production use also needs saturation counters, be-
cause a sudden change in value range can make the previous
scale unsuitable.

3.3
Fragment-aligned INT4 decode
3.3.1
Why decode needs a different path
Let P be the number of projection-weight elements in one
layer. Excluding small metadata fields, the minimum num-
ber of bytes read during decode is
Bdecode = Pw + 2BTHkvDk,
(12)
Here, w is the number of bytes per weight, and k is the
number of bytes per cached K or V element. For the 8B
shape at batch one, the projection weights contain 218.1
million elements. These weights occupy 436 MB in BF16,
218 MB in E4M3, or 109 MB in INT4. Reducing w and k
therefore directly reduces the data that must be read and can
lower latency.
On H100, the small-M decode kernels cannot use an INT4
MMA that directly reads these packed values. They also
have too few rows for the large FP8 WGMMA shapes used
in prefill. FUTRANSFORMER therefore expands low-bit
values into 16-bit MMA operands. Its layouts allow this
expansion to happen while building the fragments, without
a separate dequantization stage.
3.3.2
INT4 KV-cache mirror
FUTRANSFORMER keeps the BF16 KV cache as the main
copy for prefill and compatibility, and maintains an INT4
copy for decode. Each byte stores two signed 4-bit values.
Each token and KV head has one FP32 scale, calculated as
amax /7.
Scaling is performed outside the elementwise loop. For K,
the scale is applied to the completed query–key dot prod-
uct. For V, it is applied to the attention probability before
the probability–value MMA. The kernel therefore avoids
scaling each unpacked element separately.
A shared-memory table with 256 entries maps each packed
byte to two FP16 values. One lookup expands both nibbles
into the pair format needed by an MMA fragment. The
table does not depend on the token scale, because scales are
applied after accumulation.
Keys follow the byte order required by the B operand of
mma.sync.m16n8k16. Each lane reads a contiguous
segment the size of its fragment and uses byte-indexed
lookups to fill the operand registers directly. This avoids cre-
ating a dequantized K tile and moving it through shared
memory. V stays in natural channel order because the
probability–value MMA groups values differently. It is
transposed through shared memory before use.
The attention CTA quantizes the new cache row that it will
use in the current decode step. The asynchronous-copy


pipeline loads cache scales together with their K/V tile.
This keeps cache updates and scale loads outside the serial
inner attention loop.
3.3.3
Hadamard transform for cache outliers
Uniform INT4 quantization can lose accuracy when a few
channels have large values. Following QuaRot and SAW-
INT4 (Ashkboos et al., 2024; Jia et al., 2026), FUTRANS-
FORMER applies a normalized block-diagonal Hadamard
matrix H before writing each cache row. The query uses
the same transform:
(Hq)⊤(Hk) = q⊤H⊤Hk = q⊤k.
(13)
The attention output is transformed back once per query
row. The transform uses a Walsh–Hadamard butterfly im-
plemented with registers and warp shuffles. Each cache row
is rotated once when it is written. The query and output
are each rotated once per decode step. The attention loop
therefore performs the same work per cached token, and
the added rotation cost does not grow with context length.
By default, each block covers the full head dimension, but
narrower blocks can also be used.
3.3.4
INT4 projection weights
Weights are quantized offline with one symmetric scale for
each output channel and each group of 128 input elements.
The nibbles follow the order required by the B fragments
of the decode MMA, so each warp can load a contiguous
weight segment for its output tile. The format defines where
each nibble is stored, not how its value is chosen. Values
can come from the library’s round-to-nearest quantizer or a
calibrated method such as GPTQ. Both quantization grids
are packed into the same layout offline.
Weights are dequantized in registers. Each nibble is inserted
into the mantissa bits of the BF16 value 128.0. A logic
operation produces packed BF16 values of the form (128 +
n, 128 + m). One packed BF16 fused multiply-add then
subtracts 136. This removes the base value 128 and the
offset of 8 used to convert an unsigned nibble to a signed
value. Each group is accumulated separately. Its group scale
is applied before the result is added to the running FP32
accumulator. The kernel never creates a full BF16 weight
tile.
For M = 1, each warp reads the weights for one output
tile and a quarter of the reduction dimension. The four
warps in a CTA combine their partial sums through shared
memory. For 2 ≤M ≤32, a skinny kernel loads activa-
tion tiles, packed weights, and scales through a multi-stage
asynchronous-copy pipeline. It uses split-K across CTAs
when additional CTAs are needed to keep the GPU occu-
pied.

EVALUATION
4.1
Experimental setup
We run the experiments on one NVIDIA H100 80GB SXM5
GPU with CUDA 13.0 and PyTorch 2.14.1+cu130. For pre-
fill and CODA measurements, the SM clock is fixed at 1980
MHz. Decode measurements use default clocks. We inter-
leave the compared implementations within the same run
so that they experience similar thermal conditions. Unless
stated otherwise, compiled PyTorch and FUTRANSFORMER
both use CUDA graphs. Prefill results are the median of
four to eight timing invocations after warm-up. For CODA,
we alternate the two binaries over three rounds. For decode,
all PyTorch and FUTRANSFORMER candidates run in one
process over three interleaved rounds. Both comparisons re-
port median CUDA event time over repeated launches. Each
table is a separate interleaved run, so the same configuration
can differ by up to 2% between tables; each comparison
is made within one table. The per-layer tests use synthetic
inputs and weights, quantized with the library’s round-to-
nearest quantizer. The whole-model tests in Section 4.5
use the trained checkpoint and the GPTQ-packed weights
described in Section 4.8. The quantizer changes the nib-
ble values but not their number or storage positions, so it
does not change latency. The two quantizers give the same
timing within run-to-run variation. The labels 1B, 8B, 70B,
and 405B refer to layer shapes. They do not imply that a
complete model of that size runs on one GPU.
The prefill baseline is a compiled, CUDA-graphed PyTorch
block using torch._scaled_mm. It uses one activation
scale per row and one weight scale per output channel. The
baseline and FUTRANSFORMER both use FP8 projections
and BF16 attention. We calculate effective prefill throughput
from the projection FLOPs and causal-attention FLOPs:
P = H(Hq + 2Hkv)D + HHqD + 3HI,
(14)
Fprefill ≈2BSP + 2BS2HqD.
(15)
For decode, PyTorch provides an eager BF16 block and a
compiled, CUDA-graphed BF16 block. It does not provide a
directly comparable full block that combines INT4 weights
with an INT4 KV cache. We therefore state the precision of
every decode result. We also compare FUTRANSFORMER’s


BF16, FP8, and INT4 paths to measure the effect of reading
fewer bytes within the same implementation.
4.2
Prefill compared with PyTorch
Figure 1 shows prefill at batch one. Speedup ranges from
0.92× to 1.48× across the tested configurations. The 1B
shape at S = 512 is the only measured FP8 case where
FUTRANSFORMER is slower than PyTorch. Avoiding inter-
mediate activation reads and writes becomes more useful
for larger shapes or longer sequences. The 405B layer
reaches 1286 TFLOP/s at S = 2048 and stays near 1.20–
1.29 PFLOP/s across the measured range.
For the 8B shape at S = 2048, FUTRANSFORMER takes
804.2 µs, compared with 1004.5 µs for PyTorch, giving
a 1.25× speedup. This agrees with the design goal. The
projection mainloop is already close to the library GEMM
rate, so most of the improvement comes from avoiding
intermediate activation traffic and separate conversion or
cache-placement kernels.

4.4
Decode compared with PyTorch

When both implementations use a BF16 cache, FUTRANS-
FORMER is 1.3–5.0× faster than the precision-matched
INT4 block. This comparison isolates the projection kernels
and fusion. With its INT4 cache copy, FUTRANSFORMER
is 1.3–6.3× faster, and the gap is widest where PyTorch has
no matching INT4 cache. The eager INT4 block takes 848–
2604 µs and is limited by launch overhead, as is the eager
BF16 block. PyTorch’s INT4 kernel is tuned for a single
query row, so its advantage over PyTorch’s own compiled
BF16 block shrinks as rows are added: it is 1.6× faster at
batch one on 8B, 2.2× faster at batch one on 70B, roughly
even at batch 8, and 1.9–2.6× slower at batch 32. The
strongest PyTorch baseline is therefore its INT4 block at
small batch and its BF16 block at batch 32, and FUTRANS-
FORMER is 1.3–2.4× faster than whichever is faster in each
row.

shape. Lower cache precision reduces latency when cache
reads make up a large share of the total bytes.
4.5
Whole-model decode and prefill
Table 6 evaluates the complete Llama-3.1-8B model. Every
decoder layer uses the fused block, while PyTorch runs the
embedding, final RMSNorm, and LM head. We capture
one greedy decode step in a single CUDA graph and replay
it. The step takes a token as input and produces the next
token. Its timing includes the 32 block launches and reads
of the 1 GB BF16 LM-head weights, which are unchanged
by the decode-weight format. The PyTorch baselines use the
transformers implementation of the same BF16 checkpoint
with a static cache, in eager mode or compiled with CUDA
graphs. We time decode steps at positions just below the
reported context length, using 64 steps per round for five
rounds and reporting the median. Prefill uses one 2048-
token prompt at batch one. INT4 is supported only for
decode, so the INT4 rows use BF16 prefill.
The complete INT4 model decodes 2.0–2.2× faster than
FUTRANSFORMER’s BF16 model at batch 8 or below, and
1.9× faster at batch 32 and context 4096. In the latter case,
INT4 cache storage contributes about as much as INT4
weights. A step takes 11.7 ms with BF16 weights and cache,
8.8 with INT4 weights alone, and 6.0 with both. Compared
with FUTRANSFORMER’s BF16 path, the whole-model gain
is smaller than the per-layer gain in Table 3. At batch one,
the embedding and LM head add about 0.3 ms to every path.
Prefilling 2048 tokens takes 46 ms with BF16 and 27 ms
with FP8, compared with 52 ms for compiled PyTorch.
The whole-model speedup over the transformers implemen-
tation is 2.9–9.9×, larger than the 2.1–2.9× in Table 3.

Profiling the compiled PyTorch step explains this difference.
At batch 32 and context 4096, attention accounts for 89%
of its 60.8 ms step. Copy kernels take 29 ms to expand the
8 KV heads to the 32 query heads and arrange the cache for
cuDNN. The cuDNN attention kernel takes another 23 ms
to process the full 4096-entry static cache. Projections take
5.9 ms, close to 32 times the per-layer block. At batch
one, projection GEMMs account for 81% of the step, and
weight traffic explains the performance gap. The transform-
ers static-cache attention path therefore takes about ten times
as long as PyTorch SDPA on the compact cache used in the
per-layer benchmark. FUTRANSFORMER reads its 8-head
INT4 cache directly in fragment order, without expanding
the heads. This explains most of the whole-model advan-
tage. Table 6 uses BF16 PyTorch rows because transformers
has no equivalent whole-model INT4 path available in this
setup. The precision-matched kernel result is the per-layer
comparison in Table 3; the whole-model ratio also includes
these framework-level differences.
4.6
Design ablation
Table 7 uses compile-time switches to replace design ele-
ments of the INT4 decode block with earlier versions, while
keeping precision and data size fixed. Storing K in natural
order and transposing it through shared memory, rather than
using the MMA fragment order in Section 3.3, increases
latency by 16% at batch 32 and context 4096. It costs
at most 2.3% where cache reads account for only a small
share of the bytes. If per-nibble arithmetic also replaces
the byte-indexed lookup, the combined latency increase is
25%. These two changes reproduce the earlier cache de-
sign. Quantizing the new cache row in a separate kernel
between QKV and attention, rather than inside attention,
adds 1–2 µs per step. Converting weight nibbles with an
extra bias MMA, instead of register logic and FMA opera-
tions, increases latency by 9% at batch one, 20% at batch 8,
and 11% on 70B. The earlier FMA split-KV attention kernel
takes 9–17% more time than the Tensor Core INT4-cache
kernel at context 1024, and 2.4× as long at batch 32 and
context 4096. The earlier skinny BF16 projection kernel
does not support low-bit formats, so we compare it only on
the BF16 path. For the three 8B shapes, its latencies are
192, 232 and 299 µs, compared with 167, 174 and 276 for
the current kernel.

4.8
INT4 decode on a trained checkpoint
The synthetic tests isolate kernel error. To measure the qual-
ity cost of the INT4 decode path on a real model, we evaluate
the BF16 release of Llama-3.1-8B (Grattafiori et al., 2024)
on the WikiText-2 test set (Merity et al., 2017), following
the GPTQ protocol (Frantar et al., 2023). We concatenate
the test split and divide it into 141 non-overlapping windows
of 2048 tokens. Perplexity is the exponential of the mean
token negative log-likelihood. Every token is decoded one
position at a time through the production decode block of
each of the 32 layers. PyTorch runs the embedding, final
RMSNorm, and LM head, and 32 windows are decoded in
parallel. Table 10 uses a BF16 KV cache to isolate weight
quantization. Table 11 uses the INT4 cache copy and eval-
uates the complete INT4 decode block. GPTQ calibration
uses 32 random windows of 2048 tokens from the WikiText-
2 training split. GPTQ uses symmetric 4-bit weights, static
groups of 128, no column reordering, 5% damping, and an
FP64 error-feedback solve on the GPU. Using the WikiText-
2 validation split, we selected round-to-nearest quantization
for layer 1’s down projection, where Llama-3 forms the mas-
sive activations that later layers attend to (Sun et al., 2024);
the test split was used only to produce the reported numbers.
An offline packer stores the GPTQ grid in the kernel layout
and matches the library quantizer byte for byte. The kernels
themselves are unchanged.
Table 10 shows the results. The BF16 kernel path matches
PyTorch perplexity to three decimal places. For round-to-
nearest weights, the INT4 kernel path and a BF16 simulated-
quantization reference built from the same grid agree to
0.001 perplexity. Round-to-nearest INT4 weights increase
perplexity by 0.99, while GPTQ weights in the same for-
mat increase it by 0.75. For this model, choosing each
group’s scale with a mean-squared-error search, rather than
the group maximum, makes round-to-nearest quantization
less accurate.

4.9
The served path and downstream tasks
Tables 10 and 11 decode every token from the start of each
window. This isolates the decode path, but differs from the
serving workflow. Table 13 evaluates that workflow. The
first 1024 tokens of each window use BF16 or E4M3 prefill,
since INT4 is supported only for decode. The remaining
1023 positions are decoded one at a time. We score only the
decoded positions, and the cache copy contains all positions.
In the serving workflow, the complete INT4 decode block
adds 0.53 perplexity, or 9.4% over the all-BF16 path. When
every token is decoded from the first position, the increases
are 0.94 and 15.1%. The protocols differ in two ways. In
the serving test, each scored token has at least 1024 tokens
of context, and the first half of the window is processed
with higher-precision weights. FP8 prefill adds only 0.004
perplexity, and E4M3 decode weights add 0.02. Thus, the
INT4 decode weights account for the full quality cost with
either prefill path.

Variable-length prefill
Table 15 compares packed and padded execution within
FUTRANSFORMER for the 8B shape, with B = 8 and
Smax = 2048. For equal-length inputs, packing adds no
visible overhead. When one request has length 2048 and

faster because it skips most padded projection rows.

DISCUSSION AND LIMITATIONS
Baseline precision.
The PyTorch prefill comparison uses
the same projection and attention precisions, but different
activation-scaling policies. The BF16 gate/up comparison
between FUTRANSFORMER and CODA is the closest like-
for-like result, although their training and inference APIs
keep different auxiliary data. The comparison between
INT4 decode and the PyTorch BF16 reference uses dif-
ferent precisions: the reference has BF16 weights and a
BF16 cache. Comparing BF16, FP8, and INT4 within FU-
TRANSFORMER isolates the effect of storage precision.

Accuracy.
Synthetic tests cover one layer.
Trained-

and two zero-shot multiple-choice tasks for accuracy. INT4
decode increases perplexity by 9–15%, depending on the
protocol, and reduces ARC-Challenge accuracy by up to
7.6 percentage points. This is a meaningful quality loss.

warm-up. Production use also needs safe scale initialization,
saturation monitoring, and request-local state. Task accu-
racy on trained checkpoints must still be validated before
deployment.
Portability.
The implementation is designed for Hopper
fragment layouts, asynchronous copies, and resource limits.
Supporting another GPU generation requires different tile
shapes, pipelines, and packed layouts. The main principles
can still be applied, but the kernel details depend on the
architecture.

CONCLUSION
FUTRANSFORMER optimizes prefill and decode separately.
Prefill keeps FP8 GEMM throughput high and reduces
data movement between operations. It extends CODA’s
GEMM-plus-epilogue formulation with inference-specific
cache placement, fixed RMSNorm-gain folding, delayed
FP8 producer output, and packed inputs. Decode reads
fewer bytes by using INT4 weights and an INT4 KV-cache
copy. Both formats follow the layout required by the con-
suming MMA fragments, so values are dequantized close to
where the Tensor Cores use them.
On one H100, FUTRANSFORMER prefill is up to 1.48×
faster than compiled PyTorch FP8 and reaches 1.29
PFLOP/s. For the closest shared BF16 gate/up–SwiGLU
stage, FUTRANSFORMER is 1.13× faster than CODA at the
8B shape. Over the 8B and 70B shapes at batch 1 to 32,
the INT4 decode block is 1.3–2.4× faster than the stronger
of PyTorch’s two decode blocks at each point. Measured
separately, it is 2.1–3.3× faster than the compiled, CUDA-
graphed BF16 block and 1.3–6.3× faster than the same
block using PyTorch’s INT4 projection kernel. It is also
31–51% faster than FUTRANSFORMER’s FP8 path. The
complete 8B model decodes 2.9× faster than compiled Py-
Torch at batch one. On Llama-3.1-8B, INT4 weights in-
crease WikiText-2 perplexity by 0.99 with round-to-nearest
quantization or 0.75 with GPTQ in the same format. The
rotated INT4 cache adds 0.20, giving a complete INT4 block
that is 0.94 above BF16. Without rotation, quantizing the
cache alone would add 0.54. The kernel path matches a
simulated-quantization reference to within 0.001 perplex-
ity. These results support GEMM epilogues for prefill and
fragment-aligned low-bit execution for decode.
