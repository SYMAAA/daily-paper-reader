Abstract 

Conditional memory expands language-model capacity through selective lookup, but the full embedding table must remain available for ev-ery possible input. We introduce Conditional Program (CP), a compressed representation that reconstructs only the rows an input re-quests. CP represents each row by a short code and a local scale, with a reconstruction program shared across the table. We instan-tiate this representation with a Gaussian trel-lis, norm restoration and independently decod-able row records. CP’s two-bit code lowers out-put KL by 41–63% relative to 2-bit round-to-nearest. Analysis across three trained n-gram memory families shows that Gaussian-like co-ordinate statistics coexist with learned relation-ships among rows; at matched storage budgets, the shared trellis outperforms the fitted code-books and low-rank residual variants we test. For DeepSeek, it reduces table storage from 203 GB to 51 GB, leaving room for larger work-loads when the table is kept on GPU. 

1 Introduction 

Conditional memory expands language-model ca-pacity without a proportional increase in per-token computation. It retrieves learned representations from large embedding tables, allowing a model to use only a small part of its memory for each input (Cheng et al., 2026; Liu et al., 2026). This makes higher capacity attractive under limited compute budgets, but the tables still occupy substantial stor-age. Moving them from accelerator memory to host memory changes where that cost is paid without reducing it. Compressing conditional memory presents a dif-ferent challenge from conventional LLM weight compression. Although its embedding tables con-tain learned parameters, they are accessed through sparse, input-dependent lookups rather than dense

computation. Existing LLM compression meth-ods primarily target dense model weights, leaving the distinct access patterns of conditional memory largely unaddressed. Conditional memory instead requires reducing the footprint of the entire table while preserving independent access to individual rows and the information they provide to the model. Can conditional memory be stored more compactly while reconstructing only the entries needed by the current input? We propose Conditional Program (CP) , a rep-resentation that stores instructions for reconstruct-ing each entry through a shared decoder. Our hy-pothesis is that a compact shared reconstruction rule, together with short row-specific codes and local scales, can preserve the signal that the model consumes from the table. An input selects which en-tries to reconstruct, so the extra work is confined to the rows it accesses. This exchanges storage across the full table for reconstruction work on a small subset, carrying the selective use of conditional memory into its compressed representation. Specifically, CP represents each row with a short code and a local scale, using a decoder shared across the table. We model normalized row con-tents as the accumulation of many small learning contributions dispersed across coordinates; when these contributions are weakly dependent and none dominates, a Gaussian source approximation fol-lows from a central-limit argument. Therefore, we encode rows in their stored coordinate system with a shared Gaussian trellis (Tseng et al., 2024b). The local scale restores the decoded vector’s norm, and independently stored row records allow the run-time to fetch and reconstruct only requested entries (Figure 1). At two bits, CP reduces table storage by roughly four- to eightfold, with most reported task scores remaining close to their original values. 2 Preliminaries 

2.1 Conditional Memory as Selective Lookup 

We consider conditional-memory table E ∈ RN ×d,where each row ei ∈ Rd stores a learned repre-sentation. For an input x, let A(x) ⊆ { 1, . . . , N }

denote the requested row addresses. N-gram-based conditional memory determines row addresses by hashing input n-grams independently for each or-der and head. Each token retrieves a fixed number of rows, so the accessed memory is 

EA(x) = {ei | i ∈ A(x)}, |A(x)| ≪ N. (1) Because the addresses are computed directly from the input tokens, retrieval does not require scanning or computing over the entire table. The retrieved embeddings are incorporated into the model’s hidden states through a readout op-eration. Let e(x) denote the concatenation of the retrieved rows and h the current hidden state. The readout can be expressed as 

h′ = h + R(h, e (x)) , (2) where R is a model-specific operation that may in-volve linear projections or input-dependent gating. The resulting hidden state is passed to subsequent network layers, so errors in the retrieved embed-dings can propagate through the readout and affect the model’s final predictions. 

2.2 Compressing Conditional Memory 

The storage footprint of a compressed table and the cost of accessing an individual row are dis-tinct quantities. Compression can reduce storage by encoding or transforming multiple rows jointly, but such representations may couple them within a larger reconstruction unit. Consequently, accessing a single row may require fetching or decoding a larger block of data. Thus, a smaller compressed table does not necessarily imply efficient access under sparse lookup. Let C(E) denote a compressed representation of the table and D(C(E), i ) the reconstruction of row 2i. Preserving selective access requires that each re-quested row can be reconstructed without decoding unrelated rows: 

ˆei = D(C(E), i ), i ∈ A(x). (3) The compressed representation must therefore re-duce the full table’s footprint while confining data fetching and reconstruction to the requested entries. Beyond selective access, compression must pre-serve the information that retrieved embeddings provide to the model. A conventional measure of reconstruction quality is the mean squared error

3 Conditional Programs 

3.1 Conditional Program Representation 

We propose Conditional Program (CP), a com-pressed representation that preserves the selective access pattern of conditional memory. Rather than storing each embedding directly, CP represents each row with a short code and a reconstruction rule shared across the table. Specifically, each row 

ei is represented by a code ci and a local scale αi,and reconstructed through a shared function f :

ˆei = αif (ci). (6) The reconstruction function is shared across the table, while each row retains only its code and scale. Since reconstruction is performed only for requested rows, CP exchanges storage across the full table for computation on a small subset. The key challenge is to construct a shared re-construction rule that accurately represents diverse learned embeddings using short codes. We sepa-rate each row’s magnitude from its contents and define the normalized vector zi = √d e i/∥ei∥2.For a code rate b, let Cb denote the set of admissible codes. A natural encoding objective is to select a code whose reconstruction best approximates the normalized row:

3.2 Gaussian Source Modeling 

Conditional-memory embeddings are learned through repeated updates from diverse inputs and contexts. In hashed n-gram memories, for exam-ple, multiple n-grams may map to the same row, allowing different training signals to contribute to a shared representation (Cheng et al., 2026; Liu et al., 2026). When such contributions are dis-tributed across many coordinates, an approximately isotropic direction provides a useful intuition for the resulting representation. In high dimensions, isotropically distributed directions exhibit approxi-mately Gaussian coordinate statistics after normal-ization (Diaconis and Freedman, 1987). Motivated by this intuition, we model the nor-malized row contents using a common Gaussian source while keeping row magnitudes separate. Specifically, we approximate the coordinate dis-tribution of zi by a standard Gaussian distribution 

N (0 , 1) . This source model provides a common sta-tistical basis for representing different rows through a shared reconstruction rule, while row-specific codes capture their individual contents. 

3.3 Encoding and Norm Restoration 

To encode the Gaussian source, we instantiate the shared reconstruction rule using trellis-coded quan-tization (TCQ) (Marcellin and Fischer, 1990; Mao and Gray, 2010). TCQ represents a sequence of 3values through a path of state transitions, allowing reconstruction values to be selected jointly rather than quantizing each coordinate independently. We use a Gaussian HYB bitshift trellis with tail-biting. For each row, the encoder searches for a low-error path through the shared trellis and stores its transi-tion symbols as ci. The reconstruction function f

recovers the corresponding vector from these sym-bols using a small shared lookup table and arith-metic operations. All rows use the same coding rule and code rate, without an additional coordinate ro-tation. Although the shared source model describes nor-malized row contents, the magnitude of each em-bedding also affects the signal passed to the model. A least-squares reconstruction scale can shrink the decoded vector when its direction differs from the original row. CP instead restores the original row norm by setting αi = ∥ei∥2/∥f (ci)∥2. This pre-serves the magnitude of the learned representation, even when doing so increases coordinate recon-struction error. The scale is computed once during encoding and stored with the corresponding row. 

3.4 Independent Storage and Selective Execution 

CP stores each row as an independently address-able record containing its compressed code and local scale. For a row of dimension d encoded at b

bits per coordinate, storing one 16-bit scale gives a rate of b + 16 /d bits per parameter before align-ment. The shared reconstruction rule incurs only a table-wide storage cost. Because each record can be addressed independently, compressed rows can be fetched and cached without accessing unrelated entries. At inference time, the original address function determines the requested rows A(x). For each ad-dress i ∈ A(x), CP fetches the corresponding code and scale, reconstructs the embedding using Equa-tion 6, and passes it to the existing readout in the original lookup order. A fused kernel performs fetching and reconstruction for the selected records without decoding unrelated rows. The address func-tion, backbone parameters, and downstream com-putation remain unchanged. 

4 Experiments 

We evaluate how well CP preserves model qual-ity under reduced table storage. We first compare downstream task performance at low bit rates, then examine the trade-off between storage and output-distribution fidelity across a wider range of rates. 

4.1 Experimental Setup Models. We evaluate Conditional Program (CP) on three models that employ n-gram lookup tables: DeepSeek, Qwen, and LongCat, as described in Section 2.1. To isolate the effect of compression, we compress only the lookup tables while keeping all other model components unchanged. 

Benchmarks. To assess the impact of compres-sion across different model capabilities, we eval-uate 40 tasks spanning five categories: common-sense, knowledge, reading comprehension, mul-tilingual understanding, and math and code. Be-yond knowledge-intensive benchmarks, we include GSM8K and HumanEval to evaluate mathemati-cal reasoning and code generation, both of which require generated answers. Table 1 presents seven representative benchmark columns from this suite. 

Baselines. We first compare against the origi-nal lookup tables and table removal, where every lookup returns zero, to assess the contribution of the stored entries. For quantization baselines, we include round-to-nearest (RTN), which indepen-dently rounds values to the nearest quantization level, and NVFP4 and MXFP4, which use four-bit floating-point formats (Rouhani et al., 2023). To further examine the benefits of CP’s design, we adapt the trellis quantization of QTIP (Tseng et al., 2024b), originally developed for dense weights, to lookup tables. Specifically, we construct a trellis-based baseline with within-row rotation and a global scale shared across the table, allowing us to distinguish the benefits of trellis quantization from those of CP’s row-wise magnitude separation. 

4.2 Results Benchmark Performance. We first examine whether CP can substantially reduce lookup-table storage while preserving model performance. As shown in Table 1, CP compresses the original ta-bles by approximately 4 to 8 times while retaining most of their benchmark performance. In particular, CP largely preserves performance on knowledge-intensive tasks where removing the lookup table causes substantial degradation. Compared with ex-isting quantization methods, CP outperforms RTN on the knowledge benchmarks for Qwen and Long-Cat, while achieving comparable performance to QTIP in the paired evaluations. 5.1 Selective Lookup Lookup layouts. CP stores each row as an inde-pendent record, allowing only the requested rows to be fetched and reconstructed. In contrast, QTIP’s tiled representation distributes each row across mul-tiple code fragments. To enable selective access with this layout, we implement a tile-window de-coder that retrieves only the bit windows needed for the requested rows rather than entire tiles. We compare this decoder against our fused row-wise decoder under identical lookup requests, a two-bit code rate, and per-row scale storage. The tiled base-line uses random payloads, while CP uses encoded model tables, so this experiment isolates access cost rather than reconstruction fidelity. 

Lookup latency. We replay lookup requests from 4,096-token sequences constructed from held-out FineWeb-Edu text using the DeepSeek tokenizer on a single H200 GPU. Each token requests 48 rows across two Engram layers. With tables stored in GPU high-bandwidth memory (HBM), CP com-pletes the requests in 0.190 ms, compared with 0.221 ms for the tile-window decoder. When ac-cessing pinned host DRAM over PCIe, the corre-sponding times are 6.54 ms and 10.78 ms. These results demonstrate that CP’s row-wise representa-tion supports efficient selective lookup, with partic-ularly large benefits when accessing tables across PCIe. We report the mean of five independent run medians, each measured over 100 timed calls after 20 warm-up calls. Additional comparisons and memory-access analyses are provided in Ap-pendix G.1. 

5.2 Workload Capacity Experimental setup. To evaluate the serving benefits of reduced memory usage, we distribute the DeepSeek backbone and tables across four or eight H200 GPUs. Our representative workload pro-cesses eight sequences with 4,096-token prompts and generates 256 tokens per sequence. We ad-ditionally evaluate larger workloads, including a decode batch of 512 sequences and a prefill step of 65,536 tokens across 32 sequences. Table 5 sum-marizes the results. 

Four-GPU serving. With four GPUs, the origi-nal FP8 tables occupy 50.7 GB per GPU, compared with 12.7 GB for CP. For the representative work-load, CP reduces prefill latency from 64.66 s to 13.27 s and enables larger workloads that otherwise run out of memory. Compared with the four-bit NVFP4 baseline, CP also reduces the 64k-token prefill time from 59.81 s to 18.23 s, while decode times remain similar. These results show that CP alleviates GPU memory pressure and improves per-formance for memory-intensive serving workloads. 

Eight-GPU serving. With eight GPUs, the orig-inal FP8 tables fit comfortably for smaller work-loads, and step times differ by at most 2.4% when memory pressure is limited. However, CP frees an additional 19.0 GB per GPU, allowing substantially larger workloads. On the tested grid, the largest successful decode batch increases from 1,024 to at least 2,048 sequences, while prefill capacity in-7creases from 96k to at least 128k tokens. These results demonstrate that CP’s reduced memory foot-print translates into greater serving capacity, even when smaller workloads already fit in GPU mem-ory. Detailed workload configurations and measure-ments are provided in Appendix G. Together, these results highlight two complemen-tary benefits of CP for model serving. Its row-wise representation enables efficient selective lookup, while its compact storage reduces GPU memory pressure, improving serving performance and sup-porting larger workloads. 

6 Related Work 

LLM weight quantization. GPTQ (Frantar et al., 2023) and AWQ (Lin et al., 2024) use calibration activations to guide rounding or scaling, while QuIP, QuIP#, QuaRot and SpinQuant use coor-dinate transformations to make weights easier to quantize (Chee et al., 2023; Tseng et al., 2024a; Ashkboos et al., 2024; Liu et al., 2025). AQLM learns additive codebooks (Egiazarian et al., 2024); QTIP combines incoherence processing with trel-lis coding (Tseng et al., 2024b), and HIGGS uses Gaussian-optimal grids (Malinovskii et al., 2025). CP applies Gaussian trellis coding to frozen lookup rows without rotation, restoring each row’s norm and storing it independently for selective access. Because quantization can affect factual answers even when perplexity changes little (Jaiswal et al., 2024; Namburi et al., 2023; Dutta et al., 2024), we evaluate absolute task scores alongside output KL. 

Embedding-table compression. Row-wise low-bit quantization is established for recommender embeddings (Guan et al., 2019; Khudia et al., 2021); other approaches use low-precision train-ing, frequency-based mixed precision, or structures fixed during training (Yang et al., 2020; Li et al., 2023, 2024; Shi et al., 2020; Yin et al., 2021; Desai et al., 2022; Tsang and Ahle, 2023). For LLM in-put embeddings, CARVQ combines grouped resid-ual VQ with a corrective MLP trained for each model (Gou et al., 2025). The hashed tables stud-ied here share rows among colliding n-grams. CP compresses these already trained tables using their row values, with a shared decoder, no model re-training and no frequency-based bit allocation. 

Conditional-memory structure and placement. 

TN-gram replaces hashed tables with a tensor de-composition during pretraining (Zhou et al., 2026); TF-Engram and CXL-based systems address mem-ory placement and access (Ma et al., 2026b,a). TF-Engram’s hash-based compression shares slots between n-grams, whereas CP numerically com-presses the rows of an existing table. SCONE stores n-gram embeddings computed by a separate model off the accelerator (Yu et al., 2025). Product-key memories and memory layers retrieve rows through learned key search (Lample et al., 2019; Berges et al., 2024); the tables studied here use hashes of input tokens. 

7 Conclusion 

CP compresses lookup tables with row codes, lo-cal scales and a shared decoder while preserving independent access to requested rows. Across three hashed-memory models, two-bit codes reduce ta-ble storage by roughly four- to eightfold, with most reported task scores close to their original values despite some task- and model-dependent losses. Under GPU memory pressure, smaller ta-bles allow larger workloads and reduce prefill time. When memory is sufficient, complete inference steps show little speed improvement in our imple-mentation. 

Limitations 

Coverage. Our conclusions concern post-training compression of three models with hashed lookup tables; they need not extend to other mem-ory architectures, including token-indexed tables (Appendix H). Most downstream comparisons use the two primary code rates, with less task coverage at higher rates than in the KL sweep. Small task-score differences do not establish equivalence. 

Analysis. The fitted-codebook and structured-residual comparisons evaluate output KL only on Qwen, limiting their generality across models. Some equal-budget comparisons use interpolated trellis values without uncertainty estimates. The Gaussian source approximation does not establish how training produces the observed row statistics. 

Deployment. Serving measurements use a single node and eager inference; optimized engines may spend a different fraction of time on lookup. Some configurations have only one measurement run, and tested workload limits are not exact capacity thresh-olds. A.2 Output fidelity and statistics 

Each domain is tokenized with the model’s own tokenizer and cut into 2,047-token chunks: 128 per domain for web, code, math, chat and multi5 (262,016 tokens), and 16 per language for the 15 languages of multi15 (491,280 tokens), 880 chunks per setting. Documents are normally truncated to 4,000 characters, and those under 200 characters are dropped; short multi15 language sets fall back to untruncated documents. 

Statistics. All intervals are 95% percentile boot-strap intervals with seed 0. Task scores and ben-efit retained use 2,000 item-bootstrap replicates; KL uses 2,000 replicates over 2,047-token chunks, paired across settings for ratios; paired task differ-ences use 10,000 item replicates. 

A.3 Quantizers and encoding 

The trellis uses a 16-bit state, two values per step and tail-biting with two Viterbi passes. Its HYB table is built from a 512-entry k-means codebook of a 2-D standard Gaussian. The code scale factor is .95 at 2–3 bits, .90 at 3.5 bits and .85 at 4 bits on DeepSeek and Qwen; LongCat uses 1.0 at 2 bits and the same values above; at 1.5 bits the fac-tors are 1.0 and 1.05. The rate is b + 16 /d bpp; the shared lookup table is not counted for DeepSeek and Qwen and adds about 6 × 10 −6 bpp for Long-Cat. RTN stores a minimum and a scale per group, counted as 2 × 16 bits. NVFP4 has an e4m3 scale per 16 values and one fp32 scale per table (4.5 bpp); MXFP4 has a power-of-two scale per 32 values (4.25 bpp). 

Encoding cost and software. Encoding the 2-bit CP table takes about 3.1 h on 4 H200 GPUs for DeepSeek (about 12 GPU-hours), 0.83 h on 4 GPUs for Qwen, and 5.18 h summed over Long-Cat’s 12 tables. Software is PyTorch 2.14.0 and Transformers 5.17.0. The k-means table is not bit-reproducible across independent encodes, so the LS controls reuse the stored symbols of the norm-restoration tables. The Qwen RTN baseline keeps its scale and minimum in fp32 although its rate counts them as bf16. The table sizes in the main results are logical code and metadata sizes. SSD files may also re-quire page padding (Appendix G.1). The shared decoder state is negligible for these tables; omitting its few kilobytes does not change any displayed rate. The RTN metadata convention above is a storage-accounting convention: Qwen’s evaluated imple-mentation actually retains those values in fp32.

17 D Source Statistics and Alternative Representations 

D.1 Row statistics and access counts 

Table 15 compares trained rows with dimension-matched Gaussian references. Read counts come from a sample of 726,000 fineweb-edu documents. F Geometry and Error Analysis 

F.1 Gaussian coordinates with a fixed Gram matrix 

This construction establishes compatibility be-tween Gaussian coordinates and learned geome-try, not how training produces them. Initialization and intermediate checkpoints for the target mod-els are unavailable. Rotating a fixed table Z by an orthogonal matrix R keeps its Gram matrix, 

ZR (ZR )⊤ = ZZ ⊤. If R is Haar-distributed, the normalized direction of any fixed nonzero row is sphere-uniform by rotational invariance. It can be represented as h/ ∥h∥2, with h ∼ N (0 , I d). For fixed k, ∥h∥2/√d → 1 in probability, so the first k

coordinates scaled by √d converge in distribution to N (0 , I k); see Diaconis and Freedman (1987) for finite-dimensional approximation results. The same rotation applies to every row, preserv-ing all learned pairwise geometry and rank. Rows can remain correlated, including a rank-one table, and a unit vector’s full coordinates obey a fixed-norm constraint. The construction is a compatibility argument for source statistics. Actual trained coor-dinates require the empirical checks in Section 4.3; it does not model the optimizer or establish that the complete network is invariant to a coordinate change with the consumer held fixed.

G.1 Records and lookup kernels 

Each CP row is a fixed-size record. The record holds the trellis bitstream of the row and one bf16 scale αi (Section 3). A b-bit code on a d-value row takes bd/ 8 bytes, and the scale adds 2 bytes. The rate is therefore b + 16 /d bpp. For DeepSeek at 

b = 2 and d = 256 , a record is 64 + 2 = 66 B, or 2.06 bpp. For Qwen at d = 160 , it is 40 + 2 = 42 B, or 2.10 bpp. On SSD the records are aligned so that no record crosses a 4 KB page, and one row is one read. G.3 Caching and host placement 

In the DeepSeek host-memory tests, compressing the table from 202.7 to 50.7 GB saves capacity and speeds up isolated lookups. Lookup accounts for less than 1% of a forward step in our eager implementation without graph capture, so complete step time changes little; the backbone remains on the GPU. Figure 4 comes from a simulation of a static hot-row cache. The cache holds the rows with the highest FineWeb-Edu read counts (Appendix D.1), and we evaluate it on held-out FineWeb-Edu reads. Sensitive rows. Most PLE rows have per-row kurtosis 3.3–3.5, moderately above the Gaussian value of 3. The BOS row and the rows of about 100 frequent tokens have heavy tails. These rows are read in a few sensitive layers, and they dominate the loss. At 2.0 bpp without rotation, QTIP gives a worst-domain KL of .106 on E2B and .162 on E4B (Table 26). Keeping the BOS row and the top-100 rows in bf16 costs 0.006 bpp and lowers these to .027 and .028. This gives similar worst-domain KL to QTIP with rotation (.033 and .029). On E2B-it, rotation is better (.126 against .140). These token-indexed tables therefore require a different treat-ment of sensitive rows from the uniform, unrotated representation in Section 3. In the tested hashed ta-bles, protecting sequence-start rows changes aggre-gate KL by at most 1% on DeepSeek and LongCat (Table 20 in Appendix E.3). 

Predicting model sensitivity. Table statistics alone did not predict this effect. Before measur-ing E4B-it, we fixed a prediction of the rotation KL ratio from per-layer kurtosis. The prediction was .21, and the measurement was .877. The table-side part was right: the MSE ratio without and with ro-tation was 1.74 predicted and 1.78 measured. The step from MSE to KL failed. When only layer 10 is quantized without rotation, KL is .121 on E4B and .004 on E4B-it. The two layers have similar statistics, so the gap lies in model sensitivity. We found this explanation after the prediction missed, so it is post hoc. A second prediction, also fixed be-fore the measurement, gave the correct decision for both gemma-3n models and the correct magnitude for neither. 

Layer-level norm adjustment. On PLE, a layer-mean norm adjustment on top of QTIP’s global scale changes worst-domain KL in both directions. It raises it by 6.3% and 9.0% on E2B-it and by 6.0% on E4B without rotation. In the other five settings (E2B, E4B with rotation, gemma-3n) it lowers it by 3.9–79.8%.
