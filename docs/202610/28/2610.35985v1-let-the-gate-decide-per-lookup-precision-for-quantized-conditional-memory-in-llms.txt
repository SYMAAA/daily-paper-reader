# ABSTRACT 

Conditional memory layers, such as DeepSeek’s Engram, attach large hashed n-gram tables to a language model, and removing them from DeepSeek-V4.1-Flash costs 36 .8 PopQA points. Low-bit quantization loses long-tail facts first, and the standard remedy, giving more bits to frequently accessed rows, backfires: refining lookups by access frequency is worse than refining them at random. We trace this to the gate that scales each retrieved row. A lookup’s quantization error is weighted by its gate, which is small for frequent n-grams, large for the rare n-grams of long-tail entities, and computable from a 1-bit code. GateRQ therefore stores each row as a ladder of 1-bit residual codes, keeps level 1 in GPU memory to compute the gate, and reads deeper levels only for the lookups the gate ranks highest. Without retraining, GateRQ cuts GPU table memory by 7.8× on DeepSeek-V4.1-Flash, which raises vLLM throughput by 11% –31% over FP8 tables, while losing about 1 PopQA point at 

1.50 bits read per lookup and 0.2 points at 2.10 bits across two models. 

Keywords conditional memory · Engram · quantization · residual quantization · LLM inference 

# 1 Introduction 

Recent large language models (LLMs) place part of their parameters in conditional memory : hash tables, keyed by the preceding n-gram, that sit beside the Transformer backbone, as in DeepSeek’s Engram [1] and Qwen’s Per-Layer Embedding (PLE) [2]. Each token retrieves a fixed number of rows, and a gate computed from the current hidden state scales the retrieved vectors before they enter the residual stream. The tables thus add many parameters at little compute cost, and they hold much of the model’s factual knowledge. Zeroing them in DeepSeek-V4.1-Flash costs 36 .8 points on PopQA [3], a benchmark of questions about long-tail entities, more than two thirds of its accuracy; the answers stay well formed, but the facts are wrong. The tables are also large: 203 GB ( 189 GiB) in FP8, 40% of the checkpoint. On a node of 8 RTX PRO 6000 GPUs, keeping them in GPU memory takes 23 .6 GiB on every GPU and leaves a KV cache nine times smaller (as reported by vLLM) than when they are offloaded; offloading them instead pins all 189 GiB in host memory. Much of what these tables contribute is long-tail knowledge: facts about rare entities, such as the author of a little-known novel, that the backbone does not recover on its own. Quantization, the natural way to shrink the tables, erases exactly these facts first (Section 3), so a compression budget should not be spread evenly across rows. Recommender systems, whose embedding tables face the same pressure, have a standard rule for deciding which rows to keep precise: the frequently accessed ones, which receive larger dimensions [4] or higher precision [5, 6]. The rule rests on an assumption: every access contributes equally to the output, so frequent rows, read most often, accumulate the most quantization error. This assumption does not hold for conditional memory. Each retrieved row passes through a gate before it enters the residual stream, so its quantization error is paid at every lookup, scaled by that lookup’s gate (Section 3.1). The gates, arXiv:2610.35985v1 [cs.LG] 26 Oct 2026 Let the Gate Decide: Per-Lookup Precision for Quantized Conditional Memory moreover, run against frequency: frequent n-grams are mostly function words and common phrases, which receive small gates, whereas the rare n-grams of named entities receive large ones. In the question “Who is the author of The Pianoplayers ?”, the gate is smallest at the token The and largest on the three tokens of Pianoplayers (Figure 1a). Over PopQA questions, rows seen more than a thousand times serve a third of the 2-gram lookups of block 2 but, under uniform quantization, carry under 4% of the output error (Figure 1b). A frequency rule therefore spends its bits where they matter least: choosing lookups to refine by frequency does worse than choosing them at random (Sections 3.2 and 5.2). One might hope to repair the rule instead, ranking rows by their expected gate rather than by frequency. This helps, but it still misses many important lookups, for two reasons. The rows that matter most belong to rare n-grams, which a counting corpus sees too seldom to estimate their gate; and even for common rows, the gate changes with context and can be large in one sentence and near zero in another (Section 3.2). Precision should therefore be decided per lookup, from the gate at hand. This seems to require the very precision one wants to save, since the gate is computed from the retrieved rows. It does not: the gate is insensitive to quantization, and gates computed from a 1-bit code closely match those computed from the FP8 table ( r ≥ 0.989 ; Section 3.2). Whether a lookup needs higher precision can thus be decided before any high-precision data is read. GateRQ (gate-driven residual quantization; Figure 2) combines two pieces. The first is a code whose precision can be raised after a row has been read: each row is stored as a ladder of 1-bit residual codes, with level 1 in GPU memory and deeper levels in host memory. The second is a rule that decides, per lookup, how far up the ladder to go: every lookup reads level 1 to obtain its key and gate, and under a fixed budget of bits per lookup, the lookups that the gate marks as most important fetch deeper levels, which refine only the value. Precision thus becomes a property of each access rather than of the stored row. Our contributions are as follows: • Analysis. We show three properties of quantization error in gated conditional memory: the gate error is negligible, so the gate can be computed accurately from a 1-bit code; importance runs against access frequency, so frequency-based allocation fails; and importance is concentrated in a few lookups whose identity depends on context, so row-level statistics cannot find them (Section 3). • Method. We propose GateRQ, a post-training scheme that stores each row as a ladder of 1-bit residual codes and uses the gate computed from the first level to choose how many levels each lookup reads. It needs no retraining, keeps the model’s gating mechanism intact, and applies to any codec that can encode residuals (Section 4). • Evaluation. We evaluate on two models, three codecs (trellis-coded quantization, TCQ; integer, INT; product quantization, PQ), and two read budgets ( 12 settings). At the same number of bits read per lookup, gate-based selection beats selection by expected gate, at random, and by access frequency in all 36 paired PopQA comparisons. With TCQ [7, 8], reading 1.50 and 2.10 bits per lookup costs about 1 and 0.2 PopQA points relative to FP8 and is statistically indistinguishable from reading the full two- and three-level ladders, which take 0.63 –1.20 more bits per lookup (Section 5.2). • System. In vLLM [9] on 8 RTX PRO 6000 GPUs, GateRQ cuts the table memory from 23 .6 to 3.0 GiB per GPU, which enlarges the KV cache 8.1× (as reported by vLLM) and raises throughput by 11% –31% over FP8 tables in GPU memory. Against FP8 host offloading, it matches throughput (within 1.5% ) with 26 –49 GiB of pinned host memory instead of 189 GiB (Appendix H).

Observation 2: Access frequency runs against importance. 

With the gate error set aside, the cost of quantizing a lookup scales with its importance It,j in Equation (5). Access frequency, the usual proxy for how much a row matters, points the opposite way. In the PopQA question of Figure 1a, which FP8 answers correctly and the 1-bit table does not, the 2-gram rows read at The were seen about half a million times in our counting corpus ( 115 M RedPajama tokens), yet the gate there is only 0.035 ; the rows read at the three tokens of Pianoplayers were seen at most 15 times, yet receive the largest gates in the question ( 0.20 –0.26 ); counts are medians over the eight 2-gram heads of block 2, and gates are those of one branch. The pattern holds over 4,000 

questions (Figure 1b). Among the lookups of the eight 2-gram heads of block 2, rows seen more than 1,000 times serve 

32% but carry only 3.8% of the importance, whereas rows never seen in the counting corpus serve 14% and carry 23% ;over all 24 heads, the frequent rows serve 13% of the lookups and carry 2.0% . Gate and access count are negatively correlated in every layer, n-gram order, and text we measured: Spearman −0.40 for the 2-gram heads of block 2 on PopQA, and between −0.02 and −0.63 across layers, orders, and English, Chinese, and code text (Appendix C.4). Both factors of importance contribute: the gate alone lowers the importance share of rows seen more than 1,000 times from 32% to 11% , and their smaller norms lower it to 3.8% .Allocating precision by frequency fails accordingly: choosing lookups by the frequency of their rows is worse than choosing at random. Giving extra precision to the 41% of lookups with the most frequent rows, the share refined in the 1.50-bit setting of Section 5.2, removes only 26% of the error in Equation (5) that giving it to all lookups would remove, whereas a random 41% removes 41% (Figure 4 in Section 5.3). 

Observation 3: Importance is concentrated in a few lookups, and context decides which. Importance is highly skewed across lookups. On held-out English text, the top 10% of lookups carry 48% of the importance in block 2 and 69% in block 15 ( 50% and 47% on RACE passages); on PopQA, the top 1% in block 15 alone carry 54% 

(Appendix C.4). A small budget could thus remove much of the error, if it reached the right lookups. Statistics of their rows cannot find them, for two reasons. First, many of them read rare rows, for which there is too little data to estimate an expected gate: rows never seen in the counting corpus alone carry 23% of the importance of the 2-gram lookups (Figure 1b), and 12% over all heads. Second, the gate of the same row changes sharply with context (Figure 1c). In block 15, the row that a 2-gram head reads for a good has a gate energy of 45 .6 × 10 −3 in key to a good holiday 

and 0.8 × 10 −3 in there is a good and clear reason , and its lookups spread by a factor of 4.4 between the 10th and 90th percentile, as those of a typical row do: across the rows looked up at least 20 times in RACE passages, the 90th-percentile lookup of a row has 4.3 times the gate energy of its 10th-percentile lookup in block 15, and 2.0 times in block 2 ( 8.8 and 2.1 on held-out English text; Appendix C.4). Row-level statistics of the gate are therefore no substitute for the gate itself. Per lookup, ranking by the current gate beats ranking by the row’s expected gate in every setting we test (Section 5.2). Together, the observations call for a scheme that reads a cheap 1-bit code for every lookup to obtain its gate (Obser-vation 1), ranks lookups by that gate rather than by statistics of their rows (Observations 2 and 3), and spends the remaining bits only on the lookups that rank highest. Section 4 develops GateRQ along these lines.

# 5 Experiments 

5.1 Setup Models and benchmarks. We evaluate two conditional-memory models: DeepSeek-V4.1-Flash and Qwen3.8-Flash-Next, with row dimensions 256 and 160 , respectively (Section 2). Benchmarks cover factual question answering on PopQA [3], TriviaQA [14], and NQ-open [15], and Chinese multitask knowledge on CMMLU [16]. All evaluations use the full test sets, with 14 ,267 , 9,960 , 3,610 , and 11 ,582 questions, respectively. Appendix F.2 gives the protocol. 

Baselines. We compare with the FP8 tables and uniform reconstruction using one, two, or three complete residual levels. We also evaluate three selection rules in the same setting: refine lookups by the row’s expected gate energy (prior ), by access frequency ( frequency ), or uniformly at random ( random ). Each rule uses the same ladder and per-level refinement fractions as GateRQ; all mixed configurations compute keys and injection gates from level 1, whereas uniform configurations use the full selected depth. These are controlled selection baselines, not separate external mixed-precision methods. 

Implementation. Quantizers are calibrated on 65 ,536 rows per head, and access counts are collected from 1.15 × 10 8

RedPajama tokens [17]. We use TCQ [7, 8], INT1 with an E4M3 scale per 32 elements, and PQ1 with 256 centroids per 8-dimensional subvector and a row scale [18]. We report logical bits per looked-up element, including scales, and evaluate two read budgets, 1.50 and 2.10 bits per lookup with the TCQ and PQ ladders. # 6 Conclusion 

Quantizing conditional-memory tables comes down to deciding which lookups deserve more bits, and the answer is the gate, not access frequency: the gate scales each retrieved row and can be computed from a 1-bit code. GateRQ stores each row as a ladder of 1-bit residual codes and reads deeper levels only for the lookups that the gate ranks highest. Across DeepSeek-V4.1-Flash and Qwen3.8-Flash-Next and three codecs, it beats the other selection rules in all 36 

paired PopQA comparisons at the same bits read per lookup, and with TCQ it is within 0.2 PopQA points of FP8 at 

2.10 bits, while cutting DeepSeek’s table memory from 23 .6 to 3.0 GiB per GPU and raising vLLM throughput by 

11% –31% over FP8 tables in GPU memory.

# A Related Work 

Efficient Engram. Engram [1] keeps its tables off the backbone’s critical path: row IDs depend only on tokens, so the tables can sit in host memory and be prefetched. Follow-up work revisits how the tables are parameterized, stored, and used. 

Different parameterizations, trained with the model. TN-gram replaces the hash tables with CP factors shared across 

n-gram orders and matches Engram’s validation loss with 20–27% fewer memory parameters [19]. FactorEngram stores sparse coefficients over a shared dictionary and gates each dictionary vector separately [20], and Lngram addresses its tables with discrete codes learned from hidden states instead of token IDs [21]; both improve quality at the same parameter budget. Engram-Nine gives the most frequent n-grams collision-free rows and finds no improvement in loss at an equal parameter count [22], in line with our observation that frequency is a poor guide to where capacity matters. In that small model, trained on 82M tokens, the gate favors frequent n-grams, a preference that shrinks during training; in the production models we study, the relation is reversed (Section 3.2). All of these designs require training, and the largest model among them has 8B parameters. 

Cheaper storage. TF-Engram builds phrase memories offline without training and serves them from a GPU–DRAM– SSD hierarchy, hiding SSD latency with predictive prefetching driven by an early-exit head [23]. Ma et al. [24] pool Engram tables in CXL memory shared by several hosts and reach near-DRAM end-to-end performance in SGLang. 

Selective use. Bi et al. [25] find that conditional memory helps some inputs and hurts others in scientific reasoning, and route whole inputs and layers to or away from memory with task-specific input features. GateRQ is complementary to these lines. It compresses the tables of an existing checkpoint after training, without gradient updates, and sets the precision of each lookup from the model’s own gate. It reduces what a storage hierarchy must hold and transfer, it makes a finer-grained decision than input-level routing, and it could in principle be extended to the trained designs above that keep large tables and context gates.

# D Residual Ladder 

Quantizers. Each code quantizes one level at a time, and a level k > 1 encodes the residual that the earlier levels leave, with the same quantizer. TCQ [7] uses QTIP’s bitshift trellis [8] with a 16 -bit state, the computed 3INST codebook, tail biting, and one FP16 scale per row. PQ [18] divides a row by its FP16 norm, cuts it into de/8 sub-vectors of eight dimensions, and codes each with one of 256 codewords (an 8-bit index, one bit per element). INT rounds to nearest within groups of 32 elements that share an E4M3 scale (at one bit the values are ±s/ 2); the scale is chosen by a search over clipping values that minimizes the mean squared error, and the tensor-level coefficient is a power of two. We apply no rotation: the rows are already close to independent Gaussian vectors (Appendix C.2), and a rotation brought no gain. vLLM reads DeepSeek’s tables only as FP8 with E8M0 scales, so every level table of DeepSeek is re-encoded in this format, which is exact for INT and adds 0.063 –0.065 percentage points to the relative error of PQ and TCQ.

# F Implementation and Evaluation 

F.1 Native Implementation 

We implement GateRQ for DeepSeek-V4.1-Flash as a patch of vLLM 0.30 [9] that replaces its Engram layer and is loaded when the module is imported, so the vLLM installation stays unmodified. Level 1 of every row (the 1-bit code and its FP16 scale, 34 bytes) stays in GPU memory, 3.04 GiB per GPU. Levels 2 and 3 are packed into fixed-size records of 36 or 68 bytes and kept in one pinned host copy per node, which the eight ranks share through /dev/shm :

25 .8 GiB at 1.50 bits and 48 .6 GiB at 2.10 bits, against 188 .7 GiB for FP8 tables offloaded to host memory. Only DeepSeek has a native implementation; the accuracy results of both models come from an emulation of the same read rule inside vLLM (Appendix F.2). In a forward pass, the ranks look up the level-1 codes of their heads and all-gather them ( 36 bytes per lookup instead of the 512 bytes of a bf16 row), decode them, and compute the gates and the importance estimate of Equation (9). One Triton kernel computes the quantile thresholds of the batch for up to 16 ,384 lookups per layer, and larger batches use a sort. Each rank then copies the records of the selected lookups of its own heads from host memory into a fixed-size GPU buffer, and the ranks all-gather these buffers; fixed-size buffers with masks keep the path compatible with CUDA Graphs. The fused key and value projection is split without copying, so that deeper levels refine only the value (Algorithm 1), and every rank decodes the residuals of all heads, so no all-reduce is needed. The serving path is synchronous, and the bytes physically transferred depend on packing and alignment, so they can exceed the logical read rate. Table 16 times the table side of one layer on one RTX PRO 6000 of a TP8 node, with cold host reads. It includes the all-gathers, the decoding, the thresholds, and the host reads; the projections, the gates, and the output are the same in all rows and are not counted. A host read costs about 20 ns per record whatever its size between 32 and 128 bytes, and level-1 codes make the all-gather 12 .7 times cheaper than for bf16 rows. At 8,192 tokens, reading the records of each rank’s own heads takes 3.0 (1.50 bits) and 2.5 (2.10 bits) times less time than FP8 in host memory, and 2.5 and 2.0

times less than FP8 in GPU memory (Figure 5). The exchange has a fixed latency, so below about 300 –500 tokens it is slower, and it is meant for prefill blocks. The throughput of Appendix H was measured with a simpler variant in which every rank reads the records of all heads, with identical outputs (rows all heads per rank ).
